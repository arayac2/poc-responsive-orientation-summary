Landscape & Portrait — what we can use

Simple answer for design: the browser already knows if the screen is wide (Landscape) or tall (Portrait). We can style differently for each. Same idea as breakpoints, but by shape — not by pixel width.

LandscapeScreen wider than tall
PortraitScreen taller than wide

The solution

Use the browser’s built-in orientation check:

ModeWhen it appliesTypical devices
PortraitHeight ≥ widthPhone upright, many tablets upright
LandscapeWidth > heightPhone sideways, most laptops / desktops

This works together with today’s breakpoints (0 / 768 / 1024 / 1680). Breakpoint = how wide. Orientation = tall vs wide shape.

Will it work for users?

~97.6%Browsers support this
YesChrome, Edge, Firefox, Safari
YesiOS & Android phones / tablets

Source: Can I Use — CSS orientation. Gaps are very old browsers we don’t target.

One thing designers should know The browser looks at the visible area, not the phone’s tilt sensor. Example: phone in portrait, but the on-screen keyboard opens and shortens the height — styles may briefly switch to Landscape. Plan layouts that still look okay if that happens.

Bottom line Yes — Landscape and Portrait are a real, widely supported browser feature (~97.6%). Safe to design for. Existing width breakpoints keep working; orientation is an extra axis when the layout needs it.

1. Use “pointer” when a width could be tablet or desktop?

Yes — for that gray zone (e.g. around 1024px), don’t guess the device name. Ask how people point:

What we checkUsually meansGood for
Finger-style pointer (coarse) Touch-first (many tablets / phones) Bigger tap targets, touch-friendly type/spacing
Precise pointer (fine) Mouse / trackpad-first (many laptops / desktops) Denser UI, hover actions, desktop typography
Don’t treat pointer as device name A touch laptop can feel like a tablet. An iPad with a mouse can feel like a desktop. Pointer = how they point, not “this is an iPad.” Still the best CSS tool for the tablet/desktop overlap.

Support ~97.4% — Can I Use · pointer / hover.

2. Pointer + OS + breakpoint together for layout & type tokens?

ComboCan we?Recommendation
Breakpoint + Landscape/Portrait Yes Use for layout shape (stack vs side-by-side)
Breakpoint + pointer (and hover) Yes Use for density / type / touch vs mouse UI
Breakpoint + orientation + pointer Yes Best full combo when a screen needs all three
Anything + OS (Windows / Mac / Linux) Only via Navigator API (JS) Not CSS tokens — eng wires platform, then pairs with layout rules
What to choose Prefer width breakpoint + Landscape/Portrait + pointer. Drop OS from the design system rules. OS doesn’t change layout the way size, shape, and input do.

3. Can we detect OS for laptop / desktop?

Not with CSS. The only practical way to read platform / OS is JavaScript’s Navigator API (e.g. userAgent / userAgentData) — not a design-token media query.

WishReality
Know Windows vs Mac vs Linux Possible only via Navigator API in code — not via CSS orientation/breakpoint tokens
Know laptop vs desktop Navigator still won’t reliably say “laptop” vs “desktop tower” — only OS / browser hints
Use it for typography tokens in the DS Possible but fragile (privacy limits, spoofing, incomplete data) — prefer pointer + breakpoint instead
For designers If a spec truly needs OS (rare), engineering must use the Navigator API in app code. Don’t expect Landscape/Portrait or breakpoints alone to name Windows / Mac.

4. Pair each method with Landscape / Portrait — does it work?

Method+ Portrait / Landscape?Notes for design
Width breakpoint Yes (CSS) e.g. tablet Landscape → 2 columns; tablet Portrait → 1 column
Pointer (finger vs mouse) Yes (CSS) e.g. touch + Portrait → large type; mouse + Landscape → denser type
Hover capability Yes (CSS) Usually with pointer; don’t rely on hover-only actions for touch
OS / platform (Navigator API) Yes, but only in app code Read OS via Navigator, then combine with orientation (CSS or matchMedia). Not a pure token/CSS pair.

CSS-only: breakpoint + pointer + Landscape/Portrait can all be required together.

With Navigator API: engineering can detect platform (e.g. Mac vs Windows), then apply layout/type when that platform and Portrait or Landscape match — e.g. “Windows + Landscape → denser type.” That needs JavaScript glue; it won’t live as a plain CSS token rule.

Practical pick Default specs: breakpoint × orientation × pointer. Add Navigator platform only when product truly needs OS-specific behavior — and expect eng to wire it, not the token sheet alone.
Bottom line for the follow-ups Spec layouts and typography with breakpoint × orientation × pointer. Need OS/platform? Only via the Navigator API in app code, then pair with Landscape/Portrait there — not as a CSS-only token rule. Laptop vs desktop still isn’t a reliable label.
