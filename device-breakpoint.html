Device type + breakpoints

Shared summary for design and engineering. Keep CML width breakpoints (0 / 768 / 1024 / 1680). Add a device-class signal (tablet / desktop / mobile) so a wide tablet does not inherit Desktop UI just because width ≥ 1024.

UnchangedBreakpoint widths stay the same
Device classUA / Client Hints / form-factor heuristic
Not pointerpointer/hover ≠ platform identity

Why this exists

Width alone cannot separate tablet and desktop when both hit 1024 (classic: iPad landscape). Product still wants Tablet UI on tablet devices, and Desktop UI on desktops at ≥1024 — including portrait.

Model Breakpoint = how wide · Device class = tablet vs desktop vs mobile · Layout = f(width, device class).

Proposed solution

  1. Detect device class in JS (platform / form-factor signals).
  2. Persist it on <html data-cml-device="…">.
  3. Combine with existing respond() / breakpoint helpers for layout.
LayerResponsibilitySignal
Device class Is this tablet / desktop / mobile? UA regex + iPad touch hack · Client Hints formFactor when available · optional screen+touch heuristic
Breakpoint Which width band? min-width 0 / 768 / 1024 / 1680
Storage Share class with CSS + components data-cml-device on <html>
Do not use pointer/hover for device class (pointer: coarse) / (hover: none) describe current input modality. A tablet with a mouse reports fine+hover and would be classified as desktop. Wrong abstraction for “real tablet.” Keep pointer for density / hit targets if needed — not for platform.

How device class is detected

We do not run all detectors as AND. It is a waterfall: try one source, if it returns a value use it; otherwise fall through. One winner → write data-cml-device once.

OrderSourceRole
1 Client Hints formFactor Use if available (Chromium). Else skip.
2 UA / platform (incl. iPad MacIntel+touch hack) Baseline — sync, almost all browsers
3 Screen + maxTouchPoints heuristic Optional last resort if you want a non-UA fallback
— Pointer / hover MQ Not used for device class 
// Conceptual waterfall — first non-null wins
device =
  clientHintsFormFactor()   // may be null
  ?? detectDeviceClassFromUA()   // always returns mobile|tablet|desktop
  // ?? detectDeviceClassHeuristic()  // optional

html[data-cml-device] = device
Recommended ship shape Boot with sync UA (#2) so first paint is stable. Optionally upgrade from Client Hints (#1) if it returns later. Heuristic (#3) only if product wants a non-UA fallback.

1) UA / platform (baseline pure JS)

type CmlDevice = 'mobile' | 'tablet' | 'desktop';

export function detectDeviceClassFromUA(): CmlDevice {
  const ua = navigator.userAgent;
  const touchPoints = navigator.maxTouchPoints || 0;

  // iPadOS 13+ often reports as MacIntel + touch
  const isIPad =
    /iPad/.test(ua) ||
    (navigator.platform === 'MacIntel' && touchPoints > 1);

  const isAndroidTablet = /Android/i.test(ua) && !/Mobile/i.test(ua);
  const isOtherTablet = /Tablet|PlayBook|Silk/i.test(ua);
  const isMobile =
    /iPhone|iPod|Android.*Mobile|Windows Phone|BlackBerry/i.test(ua);

  if (isIPad || isAndroidTablet || isOtherTablet) return 'tablet';
  if (isMobile) return 'mobile';
  return 'desktop';
}

Limits: reduced UA, spoofing, odd WebViews. Still the practical browser signal for form factor when Client Hints are unavailable.

2) Client Hints (when available)

async function detectFromUserAgentData(): Promise<CmlDevice | null> {
  const uad = (navigator as Navigator & {
    userAgentData?: {
      getHighEntropyValues?: (keys: string[]) => Promise<{ formFactor?: string[] }>;
    };
  }).userAgentData;
  if (!uad?.getHighEntropyValues) return null;

  const high = await uad.getHighEntropyValues(['formFactor']);
  const ff = high.formFactor ?? [];
  if (ff.includes('Tablet')) return 'tablet';
  if (ff.includes('Mobile')) return 'mobile';
  if (ff.includes('Desktop')) return 'desktop';
  return null;
}

Chromium-family; not a full Safari solution.

3) Optional form-factor heuristic (no UA)

export function detectDeviceClassHeuristic(): CmlDevice {
  const touch = (navigator.maxTouchPoints || 0) > 0;
  const minSide = Math.min(screen.width, screen.height);
  const maxSide = Math.max(screen.width, screen.height);

  if (!touch && minSide >= 768) return 'desktop';
  if (touch && minSide >= 600 && maxSide <= 1366) return 'tablet';
  if (touch && minSide < 600) return 'mobile';
  return 'desktop';
}

Keys off touch hardware + screen band, not current pointer — so mouse on tablet usually still lands on tablet. Convertibles can false-positive.

4) Compose + persist

export async function detectDeviceClass(): Promise<CmlDevice> {
  return (await detectFromUserAgentData()) ?? detectDeviceClassFromUA();
  // optional last resort: detectDeviceClassHeuristic()
}

export async function applyCmlDevice(): Promise<void> {
  const device = await detectDeviceClass();
  document.documentElement.setAttribute('data-cml-device', device);
}

// boot early
await applyCmlDevice();
// → <html data-cml-device="tablet"| "desktop"| "mobile">

5) How this combines with current breakpoint tokens

Think of two separate inputs. They are multiplied, not merged into new px values.

A. Breakpoint tokens (unchanged)

Just numbers from CML today:
mobile 0 · tablet 768 · desktop 1024 · desktop-large 1680

B. Device class (new)

A label on <html>:
data-cml-device="tablet|desktop|mobile"

Today: only A → “width ≥ 1024? use Desktop styles.”
After: A and B → “width ≥ 1024 and class is desktop? use Desktop styles.”

Truth table (what UI you get)

Width data-cml-device UI tier Why
500 any Mobile Below 768 token
900 tablet Tablet ≥768, class tablet
900 desktop Tablet band ≥768 but <1024 — desktop class not wide enough yet
1024 tablet Tablet Width hits desktop token, but class blocks Desktop styles
1024 desktop Desktop Width token + class both say desktop
1680 desktop Desktop large ≥1680 token + desktop class
1680 tablet Tablet (recommended) Class still blocks desktop / desktop-large

Same tokens in code — only the gate is new

// UNCHANGED — still the same token map
$breakpoints: (
  mobile: null,       // 0
  tablet: 768px,      // $cml-sys-breakpoint-standard-md
  desktop: 1024px,    // $cml-sys-breakpoint-landing-l
  desktop-large: 1680px,
);

// TODAY
@media (min-width: 1024px) {
  /* desktop styles always */
}

// AFTER — same 1024 token, plus class check
@media (min-width: 1024px) {
  :host-context(html[data-cml-device='desktop']) {
    /* desktop styles only for desktop class */
  }
}

// Tablet class keeps tablet styles from 768 up — including 1024+
@media (min-width: 768px) {
  :host-context(html[data-cml-device='tablet']) {
    /* tablet styles */
  }
}
Walkthrough — iPad landscape 1) Detector → tablet → <html data-cml-device="tablet">
2) Width = 1024 → matches desktop token (1024)
3) respond(desktop) also requires class desktop → fails
4) respond(tablet) matches (width ≥ 768 + class tablet) → Tablet UI
Tokens never changed. The class vetoed Desktop.

6) How you use respond() in components

Call sites stay the same. Authors keep writing @include respond(tablet) / respond(desktop). Only the mixin implementation gains the device-class gate. 

/* component SCSS — UNCHANGED API */
.hero {
  padding: 16px;                    // mobile base

  @include respond(tablet) {
    padding: 24px;                  // tablet tokens
  }

  @include respond(desktop) {
    padding: 80px;                  // desktop tokens
  }

  @include respond(desktop-large) {
    padding: 96px;
  }
}

What changes is what those includes compile to:

/* TODAY — width only */
@media (min-width: 768px)  { .hero { padding: 24px; } }
@media (min-width: 1024px) { .hero { padding: 80px; } }

/* AFTER — width × data-cml-device (concept for shadow DOM) */
@media (min-width: 768px) {
  :host-context(html[data-cml-device='tablet']) .hero,
  :host-context(html[data-cml-device='desktop']) .hero {
    padding: 24px;   /* tablet band; desktop class still uses this under 1024 */
  }
}
@media (min-width: 1024px) {
  :host-context(html[data-cml-device='desktop']) .hero {
    padding: 80px;   /* desktop only — tablet class never enters here */
  }
}
/* tablet class at ≥1024: still on the tablet include, not desktop */

Mixin sketch (inside _media.scss only — not in every component): 

@mixin respond($device) {
  $bp: map.get($breakpoints, $device);   // same tokens

  @if $device == mobile or $bp == null {
    @content;
  } @else if $device == desktop {
    @media (min-width: $bp) {
      :host-context(html[data-cml-device='desktop']) {
        @content;
      }
    }
  } @else if $device == tablet {
    @media (min-width: $bp) {
      :host-context(html[data-cml-device='tablet']) {
        @content;
      }
      // desktop class between 768–1023 also needs tablet-band styles:
      @media (max-width: 1023px) {
        :host-context(html[data-cml-device='desktop']) {
          @content;
        }
      }
    }
  } @else {
    // desktop-large / admin — width token; gate with desktop class if product wants
    @media (min-width: $bp) {
      :host-context(html[data-cml-device='desktop']) {
        @content;
      }
    }
  }
}
Author takeaway Keep using @include respond(…) as today. Boot sets data-cml-device. Mixin + detector do the gating. No per-component device checks in SCSS.

Performance

UA regex + a few property reads are negligible (µs). Client Hints is one async call, not per-frame work. Watchers (width MQ + attr observer) are the same order of cost as today’s breakpoint helpers — not a perf concern.

Compatibility
