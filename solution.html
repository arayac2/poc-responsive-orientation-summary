In one sentence Keep today’s “how wide is the screen?” rules as they are, and add an optional “is it tall or wide?” check on top — only when a design needs it.

How things work today

Right now our system mainly asks one question: How wide is the screen? (mobile → tablet → desktop → large desktop)

That is useful — but two screens can be the same width and still feel different if one is upright (Portrait) and the other is sideways (Landscape).

What we want to add

A second question, used only when needed:

QuestionAnswersUsed for
How wide? Current breakpoints (unchanged) Most layout steps we already have
Tall or wide shape? Portrait / Landscape Extra layout or type choices when design asks
Simple picture

Width = which “size shelf” we’re on
Orientation = whether the shelf is standing up or lying on its side

The solution we recommend

Do not rename the existing breakpoint names teams already depend on. Instead, add Landscape / Portrait as an optional extra filter when applying styles.

ApproachWhat it meansOur take
Optional filter on top of current breakpoints Same width rules + optional Portrait/Landscape Yes — recommended
Create brand-new names for every width × orientation Lots of new labels; easy to confuse; big migration No — too heavy
Replace old names with orientation-based names Forces every consumer to change No — breaking
Why this fits our system Our current “breakpoint” names are really widths. Landscape / Portrait is a different kind of fact about the screen. Mixing both into one long name would make the system harder to learn — and we already have some “Portrait / Landscape” labels that mean device frame sizes, not screen orientation. Keeping them separate avoids confusion.

How naming stays clear

Keep usingAdd (optional)
Today’s width breakpoint names (no change) Portrait / Landscape as an extra choice when needed
Existing “Ipad Portrait / Landscape” frame sizes Leave them alone — they are mock device sizes, not orientation rules

What stays compatible

  • Old breakpoint names keep working exactly as they do now.
  • Teams do not have to edit existing screens.
  • New Portrait / Landscape behavior is opt-in — only where a design specifies it.
  • If we ever reorganize internals, we can keep the old public names as aliases.

How design & product can use it

Examples you can write in a spec
  • Tablet + Landscape: show two columns
  • Tablet + Portrait: stack to one column
  • Desktop width only: keep today’s rule (no orientation needed)

Engineering applies those rules by combining “wide enough” with “Portrait or Landscape” — same idea the browser already supports (~97.6% of users).

Impact on other projects

Low. This is an additive change. Projects that ignore orientation keep behaving as today. Projects that need it can adopt screen by screen.

Pros and cons (plain language)

Recommended approachRenaming everything

Final recommendation Keep today’s width breakpoints. Add Landscape / Portrait as an optional second check. No forced migration. Use it when a layout truly needs different behavior for tall vs wide screens.
