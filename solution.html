Real solution — Breakpoint × Orientation in CML

Based on how chameleon-design works today. We want Landscape / Portrait support, without forcing anyone to rewrite existing screens.

RecommendExtend the existing helper
No renameOld token names stay
~97.6%Browsers support orientation
AvoidNew width tokens per orientation
Plain version of the idea Today we mainly ask “how wide is the screen?” We should keep that. Landscape / Portrait is a second question — “is it tall or wide?” — that we only ask when a design needs it. We add that second question onto our existing helper, instead of inventing a whole new set of width names.

1. How our system is wired today

Think of it as a chain: raw sizes → named breakpoints → grid settings → the respond helper that components actually call.

StepWhere in codeIn human terms
Width names _primitive-size.scss The shared width labels: $cml-ref-size-breakpoint-0/768/1024/1680
Product breakpoints _semantic-breakpoint.scss Friendlier names for standard / landing / admin (still just widths underneath)
Grid settings _semantic-grid.scss Each grid picks one of those widths as its starting point
What components call _media.scss → respond “When we’re at tablet/desktop/…, apply these styles” — currently width-only
JS helper utils/breakpoint.ts Same idea in JavaScript: watch width, not orientation yet
Watch out — naming trap already in the repo We already have names like Ipad-Portrait / Ipad-Landscape. Those are device frame sizes for mocks, not the browser’s “is the screen tall or wide?” check. If we also put Portrait/Landscape into breakpoint width names, people will mix them up. Keep those ideas separate.

2. What’s missing today

  • Breakpoints answer width only.
  • Orientation (tall vs wide) is a different kind of fact — not another pixel number.
  • Lots of screens already call respond(...) — renaming tokens would create a big cleanup job.
  • The JS helpers are also width-only today.

3. Options we can actually choose

Recommended A. Keep width tokens · teach respond an optional orientation

Leave every existing width name alone. Let the helper accept an optional second input: Portrait or Landscape. If you skip it, behavior stays exactly as today. 

// _media.scss — additive, non-breaking
@mixin respond($device, $orientation: null) {
  $bp: map.get($breakpoints, $device);

  @if $bp == null and $orientation == null {
    @content;
  } @else if $bp == null {
    @media (orientation: #{$orientation}) { @content; }
  } @else if $orientation == null {
    @media (min-width: $bp) { @content; }
  } @else {
    @media (min-width: $bp) and (orientation: #{$orientation}) {
      @content;
    }
  }
}
Why this is niceTradeoff
No rename, small change, opt-in, matches how CSS really works Orientation lives on the helper, not as a new “width token”

Optional add-on B. Small orientation labels (not new widths)

If we want shared names people can point to in docs/specs: 

// new file, optional
$cml-sys-orientation-portrait: portrait;
$cml-sys-orientation-landscape: landscape;

Then: @include respond(tablet, $cml-sys-orientation-landscape). Still no change to $cml-ref-size-breakpoint-*.

Avoid C. Duplicate width tokens for every orientation 

// ❌ Don’t make this the main API
$cml-ref-size-breakpoint-768-landscape: ...;
$cml-ref-size-breakpoint-768-portrait: ...;

Easy to confuse with device-frame tokens, painful to migrate, and orientation isn’t a width value anyway.

4. Naming that stays consistent with CML

KindPatternExample
Width (keep) $cml-ref-size-breakpoint-{px} $cml-ref-size-breakpoint-768
Semantic width (keep) $cml-sys-breakpoint-{context}-{step} $cml-sys-breakpoint-standard-md
Orientation labels (new, optional) $cml-sys-orientation-{portrait|landscape} $cml-sys-orientation-landscape
How you call it respond($device, $orientation?) respond(desktop, landscape)
Device frames (already exist — leave alone) $cml-ref-size-device-*-Ipad-Portrait Mock frame sizes, not media orientation

5. Recommended structure

base size
  └─ ref size breakpoint (width only)     ← keep public names
       └─ sys breakpoint / grid maps      ← keep
            └─ respond($device, $orientation?)   ← add the new question here
                 └─ CSS: (min-width) + optional (orientation)

Default: don’t pass orientation → same as today.
When design needs it: pass portrait or landscape.

8. Examples for developers

// Today — still valid
@include respond(tablet) {
  .card { display: grid; grid-template-columns: 1fr 1fr; }
}

// Orientation only
@include respond(mobile, portrait) {
  .hero { flex-direction: column; }
}

// Width + orientation together
@include respond(tablet, landscape) {
  .nav { display: flex; flex-direction: row; }
}
// What the browser sees
@media (min-width: 768px) and (orientation: landscape) { ... }

9. Do width and orientation work together?

Yes. The browser can require both: “wide enough and landscape.” Width tokens still feed the width part; orientation is the extra condition.

10. Pros / cons / recommendation

OptionCompatVerdict
A. Extend respond (+ optional orientation labels) Full Do this
B. Parallel width tokens per orientation Heavy aliases Not as the main API
C. Rename tokens to include orientation Breaking No
Recommendation Keep $cml-ref-size-breakpoint-* as the public width names. Add orientation as an optional second question on respond. Optionally add $cml-sys-orientation-* labels for clarity. Mirror in JS helpers later if components need it.
